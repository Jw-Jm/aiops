## 一、复审结论

方案已按下列发现修正，可以作为后续实施输入。启动后先执行 P0 核实与决策，再按任务依赖推进；本文本身不启动业务开发、迁移、安装或生产发布。

- 接口清单按具体 HTTP 方法与路径核对，区分 62 项现有操作和 76 项拟新增操作。现有表示静态合同存在，不代表逐项实际运行通过。
- 知识检索语义、未知模型准入及必要安全补充状态等，已有明确的 P0 责任与保守实施边界，不能在开发中自行省略。
- 当前没有发现未记录、无责任任务的方案级阻断；实际环境、运行制品、完整字段语义和生产门禁仍须按阶段核实。

## 二、已发现并修正的问题

### R01：把已有源码等同于页面已接入

**问题：**资源、调查、AI、执行等底层已存在，但原型的数据结构、路径、任务和状态并不全部匹配。

**修正：**主方案第三章区分现有主路径、已确认差异和拟补齐闭环。每片六项验收初始为待核实/待验收；P0 沿实际调用链完成精确裁决。

**后续验证：**P0-02、P8-02。不得将历史开发报告或原型测试数字复制成正式实现验收。

### R02：执行列表 GET 被误认为已有接口

**核对：**[OpenAPI](../../../api/openapi/platform-v1.yaml) 中 `/api/v1/command-executions` 当前仅有 POST；[ActionHandlers](../../../internal/httpapi/action_handlers.go) 也未提供该全局列表 GET。

**修正：**GET 单列拟新增，由 P6-01 实现有界分页、所有者/当前目标授权及状态筛选，不用全租户裸查询补界面。

### R03：把后置检查读取当作人工发起验证

**核对：**现有 `/command-executions/{executionId}/post-check` 为 GET；[sp07_postcheck.go](../../../internal/app/sp07_postcheck.go) 由 Worker 完成自动检查，报告有固定摘要和访问验证。

**修正：**保留已有 GET，原型人工复验另拟 POST `.../post-checks` 与单次尝试读取。人工复验产生独立记录，不覆盖旧报告、不再次执行命令。主方案 3.2、7.4 与任务/合同表同步。

### R04：会话重命名写操作被误认为已实现

**核对：**当前会话详情只有 GET，归档有独立 POST，未发现 PATCH 改名合同。

**修正：**PATCH 单列拟新增，P5-02 补所有者、版本与输入校验；归档和引用保留继续复用，不改成物理级联删除。

### R05：四字段模型连接与现有运行准入不一致

**核对：**[Profile.Valid](../../../internal/modelprofile/profile.go) 校验固定合同、地址与准入状态；[sp06_runtime.go](../../../internal/app/sp06_runtime.go) 要求冻结 Profile。权重、评测与准入证明不能由一次 HTTP 成功推导。

**修正：**保留四字段 UI；连接、能力、准入与质量分别记录。已准入目录由平台关联证据，未知材料保持真实受限状态。动态路由必须同步 API、Go/Python Worker 固定版本，不能仅改 Web 或数据库。

**明确边界：**默认保留现行运行门禁。如要求任意外部 URL 立即执行，须在 P0 单列合同/ADR 决策；未完成时不得以“保证接入”宣称所有模型可执行。

### R06：内置账号迁移导致历史主体或权限丢失

**问题：**直接将所有旧 subject 替换为新 UUID，会影响个人会话、调查、执行、幂等和审计。按同名登录名匹配又可能继承错误权限。

**修正：**P2 保留经核对的 `user_id → principal_subject` 映射和既有业务 subject；新用户使用稳定不透明主体。旧审计/证据不重写；迁移、默认组织和登录名唯一性由服务端确定，不接受客户端切换任意租户。

**后续验证：**P2-04、P2-05、P8-03，覆盖同名冲突、跨租户、旧个人历史和角色无自动继承。

### R07：简单内置登录降低原再次验证保证

**核对：**当前管理写入与高风险命令依赖加强验证、会话和事务内重检；[StepUpControl](../../../web/src/auth/StepUpControl.tsx) 仍跳转原认证链。

**修正：**P2-03 实现平台自己的真实再次验证与必要多因素；登记挑战/设置/恢复等补充状态，保留失效、撤销、操作绑定与事务检查。原型勾选不作为认证证明。

### R08：普通运维查询依赖管理员来源列表

**问题：**直接用管理来源列表填观测下拉框，会让普通运维人员无从选择，或暴露受控连接信息。

**修正：**P3-02 提供当前授权范围的能力/来源安全投影，复用既有资格服务，不授予管理员接口，不返回凭据与越权来源。`contracts.csv` 已登记拟定观测能力读取。模型选项同样采用授权能力投影，并核对可用 Worker，不依赖管理员模型连接列表。

### R09：原型预算字段直接扩张调查权限

**核对：**[调查创建接口](../../../internal/httpapi/investigation_handlers.go) 当前主要接收触发版本和类型，预算由后端策略控制。

**修正：**P4-05 明确合同扩展；用户可以收紧服务端允许的步骤/时间，不可以扩大上限。调查重点、固定模型、实际任务预算需有匹配的请求与历史投影。

### R10：按缩略预览做 1:1 截图验收

**问题：**现有 PNG 是工作台缩略图，无法替代正式 1440 × 960 黄金图。嵌套浮层与内部滚动也不能只比首页。

**修正：**P1-04 在固定远程环境从原始 HTML 重渲染全分辨率参考；P8-01 检查完整页面、关键滚动位置、弹窗/抽屉嵌套顺序与底部操作。动态掩码逐项登记，不放宽整页差异比例。

### R11：把组件就绪、数据资格和业务正常合并

**修正：**只读检查与安装分权，登记/连接/就绪/资格/覆盖/业务状态分别表达。无权限不等于未安装；部署完成进入数据待验收；不重装或接管第三方组件。

**后续验证：**P7-01、P7-02，验证目标驱动适用性、离线物料、安装权限、标签隔离、覆盖与实际来源资格。

### R12：计划调度和通知重试只做浏览器演示

**修正：**计划采用持久化槽位唯一派发、租约和接管围栏；默认不追赶停机积压。通知保存独立投递尝试与不确定回执，不能承诺跨外部系统绝对一次投递。

**后续验证：**P6-04、P7-03，测试双 Worker、重启、重复提交、停用和丢失回执。

### R13：知识库删除、索引或检索改变固定引用

**修正：**版本、发布、索引、归档分别持久化；只用授权已发布版本生成新引用，历史引用固定版本且重新授权。归档后恢复形成新草稿。检索语义由 P0 明确，字符串包含匹配不得宣传为语义检索。

### R14：认证切换后直接回滚旧版本

**问题：**新密码、撤销、用户和业务写入后，仅恢复旧 Web/API/身份或整库快照可能复活已撤销权限或丢失新数据。

**修正：**主方案第十章区分写入前和写入后两个边界。后者仅用兼容原生数据的已验证版本或前滚修复；整库恢复须明确停写、影响和补偿，不能自动触发。

### R15：补齐缺失功能扩大延期和运行范围

**修正：**明确本方案不恢复 KubeVirt/CDI、完整 Trace、既有禁用能力、生产发布或本机 OrbStack 运行。现有原型本地检查与正式业务远程验收分别标注，根目录正式文档保持原样。

## 三、结构与一致性检查

由 `validate-plan.py` 生成 [validation.json](validation.json)，检查：

1. 39 个任务 ID 唯一，所有依赖存在且无环；候选代码路径存在。
2. 458 个切片 ID 与固定 manifest 完全一致，无遗漏/重复；每片都有有效主任务、关联任务、候选接口、原型规格和六项待验收状态。
3. 方法+路径无重复；62 项已有操作确实出现在当前 OpenAPI；76 项拟新增操作没有误标成已有方法。
4. 模块切片数、任务数、接口数量和 README/baseline 一致；本目录 Markdown 相对链接可解析。
5. 不把设计验证结果写成正式验收通过；当前正式实现状态保持待实施。

该检查只证明方案结构和静态声明的一致性，不代替接口响应、数据库迁移、权限安全或真实运行验证。
