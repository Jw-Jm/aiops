本文件是审查任务的执行提示词，不是审查报告，也不表示已经开展全量审查。复制下方正文可发起任务。

## 提示词正文

请对 `/Users/mssc/Documents/Code/ops` 项目开展全面代码审查，并为发现的问题编写详细、可执行的修复方案。本轮只审查、验证和编写报告，不实施业务修复。

### 1. 目标与边界

审查至少覆盖：功能完整性、业务逻辑合理性、架构合理性、UI 美观与交互、正确性与 bug，以及权限和安全、数据一致性、异常恢复、并发、性能、可维护性、部署运维与测试有效性。

请遵守以下项目边界：

- 先读取根目录和各子目录适用的 `AGENTS.md`。以根目录 00～10 正式文档为最终方案依据，同时读取适用 ADR 和专项方案，区分最终目标、当前授权范围和已明确延期的需求。文件之间有冲突时列出冲突、引用与判断依据，不自行改写需求。
- 必须读取 `platform/AGENTS.md` 和 ADR-0008。KubeVirt/CDI 开发与运行验收仍然延期；可以审查相关隔离、disabled 合同和现有共享代码，不恢复虚拟化实施，不将明确延期项直接判成当前功能缺陷。
- 阅读后续适用 ADR，尤其是 SP-08、AI 问数、实时 DeepFlow 和故障链调查的范围约定。不要把旧阶段限制机械套用到后来已授权的专项。
- 不修改正式文档、业务源码、现有测试、依赖锁、数据库、身份配置和部署配置；不升级依赖、不提交、不推送、不发布。
- 允许新增本次审查报告和最小验证材料。验证脚本放在审查目录或临时目录，不改变被审查实现，不自动新增用于修复的产品测试。
- 保留所有现有未提交修改。记录审查开始时的分支、HEAD、工作区差异清单和审查基线；对审查期间发生变化的文件标记覆盖失效并复核，不能沿用旧行号或旧结论。
- 本机仅进行源码阅读及符合项目约定、无外部服务的静态或单元检查。容器、数据库、集群、模型和浏览器运行验证只在 `192.168.0.63` 的适用独立开发环境进行；不启动本机 OrbStack。
- 不修改既有 core/final 环境。先核对 `18443` 与 `18643` 各自的源码版本、静态资源、API、OIDC realm、身份和功能范围；分别报告部署观察，不跨环境借用验收结论。缺少匹配环境时继续静态审查，把相应动态验证列为待验证。
- 不执行故障注入、破坏性测试或会改变既有业务数据的 UI/API 操作。必要验证优先使用已有可回滚的独立测试夹具；需要额外环境变更时先列明具体动作和影响，再请求授权。
- 不在报告、日志、截图或命令输出中记录密码、token、OTP 密钥、私钥和真实敏感业务数据。

### 2. 先建立完整范围，不以抽样代替全量

先盘点整个项目，再按模块分批推进，优先审查高风险模块，但不能因此省略其他范围内代码。

将文件明确分类并说明处理方式：

1. 自有维护源码：后端、前端、Python 服务、CLI、Worker、迁移、SQL、策略、脚本、模板、构建和部署配置等，逐文件、逐函数、逐行阅读。
2. 测试与夹具：检查断言是否有效、边界是否真实、是否只覆盖 mock、是否将 skip 或 fixture 通过误写为运行验收。不能因属于测试目录就自动排除。
3. 生成代码与复制出的发行源码：审查生成源、生成配置、同步规则、人工修改和消费端一致性；列明生成产物及对应来源。未经逐行阅读的生成产物不得算入人工逐行覆盖。
4. 第三方源码、vendor、Bundle、锁文件和二进制：审查实际使用、依赖边界、配置、锁定、来源及相关准入证据，不宣称完成第三方实现的逐行审计。发现维护中的 fork 或人工修改时，将修改部分纳入自有源码范围。
5. 历史报告、日志、截图和归档：用于理解需求、旧问题和验证背景，不把重复文件计入源码阅读工作量，不把历史通过直接作为当前版本通过。
6. 已延期能力：单独列出延期依据及当前应保持的边界；边界失效、误开放或影响当前路径的问题仍须报告。

建立文件与函数覆盖台账。优先复用 Go 标准库 AST、已安装的 TypeScript 工具和 Python AST 生成清单；其他语言采用现有工具或人工登记，不为台账引入新依赖。

台账至少包含：文件路径、语言/类型、模块、文件总行数、函数或方法/组件/Hook 名称、起止行、实际已读行区间、调用方与下游核对状态、关联需求、检查状态、问题编号、验证状态、排除或阻塞原因。顶层初始化、声明、配置、SQL、模块级逻辑以及无函数文件也必须登记，不能只统计命名函数。

“已逐行审查”表示相应源码区间已完整阅读并检查上下文，不是逐行写解释，不是运行了搜索命令，也不是只读了函数签名。未完整阅读的文件只能标记部分完成。

人工阅读覆盖率按纳入人工逐行范围的文件和行区间计算；函数覆盖率单独列出。静态阅读、调用链核对和运行验证分别统计，不能混成一个百分比。覆盖率不代表代码无缺陷。

### 3. 审查维度

**功能完整性**

- 建立“需求 → 当前范围 → 页面/入口 → API → 服务/Worker → 持久化或外部来源 → 测试/运行证据”的追踪关系。
- 区分已实现且有当前证据、源码已实现但运行待验证、部分实现、当前范围内缺失、明确延期、需求有歧义或冲突。
- 检查菜单或按钮存在但接口缺失、后端已有而 UI 不可达、使用占位数据、失败被包装成成功、错误展示能力状态、只在 Fixture 中成立等情况。

**逻辑正确性与 bug**

- 对每个范围内函数检查输入、返回值、状态变化、错误处理、边界条件、取消和超时、资源释放，以及与调用方约定的一致性。
- 检查空值、零值、溢出、分页、排序、时间窗口、时区、重试、重复事件、幂等、竞态、事务、租约、任务接管、持久化和重启恢复。
- 修改建议必须追踪全部相关调用方、测试、夹具、配置和契约，不只检查局部函数。

**业务与架构合理性**

- 核对模块化单体及 API/Worker 分工、依赖方向、领域边界、OpenAPI 与生成契约、数据库模型、配置注册、来源适配器和能力开关是否符合当前方案。
- 检查跨模块状态、数据所有权、事务边界、重复业务规则、不可达代码和已影响维护的重复实现。
- 结合需求中的使用规模评价队列、查询、资源上限和背压；规模无依据时明确假设，不凭空设定高并发指标。
- 每条架构建议说明当前设计在什么场景导致什么具体代价，再提出最小改动。不要仅因文件长、函数长或使用单体架构就要求拆分，也不要默认引入微服务、通用框架或新基础设施。

**权限、安全与数据**

- 检查认证、双角色无继承、租户隔离、RLS、step-up、输入校验、命令执行边界、审计、脱敏、证据完整性和归档恢复等实际入口。
- 检查真实可达路径、实际权限和部署前提，区分已证实缺陷与尚待确认的风险。
- 不做对既有环境有破坏性的攻击验证。需要查询依赖漏洞时使用当前官方公告或原始披露，匹配版本和可达路径，避免仅凭依赖名称定性。

**UI 美观、交互与可访问性**

- 静态检查路由、组件、样式、状态管理、设计组件复用和前后端契约，并从真实路由/菜单建立页面清单。
- 对有匹配部署的页面做浏览器检查和脱敏截图，记录环境、版本、角色、路由、视口与状态。至少覆盖主要桌面宽度和窄屏，具体尺寸根据现有设计和目标用户确定。
- 检查信息层级、密度、对齐、留白、字体、配色一致性、表格和图谱可读性、滚动、长文本、表单反馈，以及 loading、empty、error、无权限等状态。
- 检查键盘操作、焦点、标签、对比度和关键操作反馈。主观审美建议与可复现的 UI 缺陷分别报告；不是所有审美偏好都定成 bug。
- 不只看首页，不为截图而伪造数据或绕过认证。无法进入的页面及尚未触达的状态标记待验证；静态推断不能写成浏览器已确认。

**测试、构建与运维**

- 阅读实际 Makefile、包脚本和测试前提后，选择能核实结论的现有检查。不要直接运行可能启动服务、写数据库或重置环境的全量命令。
- 记录执行命令、环境、基线、时间、退出码及关键结果；通过、失败、跳过、未运行分别登记。
- 检查构建和发行来源一致性、升级迁移、安装/重装、健康检查、配置错误、回滚与恢复路径。不能以单元测试通过替代完整运行验收。
- 复用有效检查结果；仅在源码变化、检查失败或仍有具体疑点时追加验证，不进行没有新增证据目标的重复扫描。

### 4. 审查组织与证据要求

- 每批选择一个可完整审查的模块，完成该模块所有范围内文件及相关调用链后立即更新报告和台账，再推进下一批。分批是执行方式，不是减少覆盖范围。
- 允许使用子代理按明确且互不重叠的模块并行审查；主审负责共享边界、端到端调用链、结论复核和去重。子代理报告不能直接代替主审核实，不需要为每个函数创建代理。
- 同一根因合并为一个问题，列出所有已确认影响位置。历史问题必须在当前基线复核，不能直接复制旧报告。
- 不预设必须发现的问题数量。摘要可以突出最重要的项目，但完整问题台账不限制数量；低优先级问题也不能因篇幅而丢弃。
- 有静态证据即可确认的问题不强制运行复现。证据不足的记录为候选问题或待验证项，不能与已确认缺陷混写。
- 缺少某个环境或凭据时，继续其他独立审查工作，同时保留准确的阻塞列表。不要因一个动态检查无法执行就停止整个审查。

每个问题应包含：

1. 稳定编号、类别、优先级 P0～P3、置信度和确认状态；说明优先级依据。
2. 问题标题、受影响功能、用户可见后果和影响范围。
3. 当前基线下的文件、函数、准确行号，以及最小必要代码引用。
4. 期望行为及需求/契约依据；设计建议则说明其评价依据。
5. 触发条件、输入或操作、调用链、实际行为和根因。UI 问题补充路由、角色、状态、视口和截图。
6. 已有证据、已执行的验证，以及仍未验证的部分。
7. 与同根因问题、历史问题或其他方案的关系。

P0 用于需要立即阻断的严重可达问题；P1 用于主要功能、安全或数据可靠性严重受损；P2 用于明确影响用户或维护的缺陷；P3 用于较低影响的改进。严重性与证据置信度分开，不能因为尚未验证就把严重性降低。

### 5. 为每个问题编写可执行修复方案

修复方案不止写“增加校验”“重构架构”或“优化 UI”，至少包含：

- 要达到的行为、根因和不需要扩大的范围。
- 推荐的最小完整修复，具体到模块、文件、函数或契约；非平凡逻辑可给伪代码或必要片段，不在本轮应用补丁。
- 所有关联调用方、API/schema、SQL/迁移、配置、前端、测试和夹具的联动修改；没有关联项时写明无须修改。
- 兼容性和既有数据影响；涉及迁移时说明顺序、恢复办法及不可逆部分。
- 验收场景、输入、预期结果和适用检查命令。bug 修复优先给出修复前应失败、修复后应通过的最小回归用例。
- 发布或部署影响、验证环境、风险、回滚步骤及前置依赖；不涉及发布的项写明不适用。
- 建议实施顺序和相对工作量；没有充分依据时不编造精确工期。
- 确有两条有实质取舍的可行路线时，比较收益、代价和风险并给出推荐；不为简单问题凑备选方案。
- UI 方案具体到布局、组件、文案、状态和可访问性调整，并说明如何在相同视口与数据条件下比较。

明确延期、需求歧义、环境限制和证据缺口分别列出对应处理方案，不伪装成已确认源码 bug。

### 6. 落盘交付与持续记录

输出到 `platform/docs/reviews/project-wide-<审查开始日期>/`，使用真实日期。已有同名审查目录时先核对是否为同一次任务；续审沿用原目录，新任务使用明确后缀，不覆盖历史报告。

至少交付以下文件，可按模块分目录，避免一份文档过大：

- `README.md`：基线、范围、方法、关键结论、阻塞、覆盖情况和报告索引。
- `scope.md`：所有目录/文件分类、纳入与排除依据、部署环境与源码的对应关系。
- `requirements.md`：需求追踪、功能完整性和当前阶段的差距。
- `coverage.csv`：逐文件、逐函数及无函数源码区间的覆盖台账。
- `findings.md`：全部问题与证据，可按模块链接详细文档。
- `remediation-plan.md`：按问题编号逐项给出修复方案，再汇总实施顺序和依赖。
- `ui-review.md`：页面与状态覆盖、截图索引、客观缺陷、审美建议及具体改法。
- `verification.md`：实际检查、结果、跳过原因、未验证项和后续验收安排。
- `progress.md`：已完成模块、正在审查的模块、剩余清单、重要判断和恢复审查的下一步。
- `evidence/`：必要的脱敏截图、最小验证材料和日志摘录；不复制整套第三方产物或敏感数据。

使用中文，解释清楚问题对使用者的影响；保持引用准确。文件之间用相对链接和稳定问题编号关联，避免多处复制导致内容不一致。

持续完成授权范围内的审查。每批结束就将成果落盘，不等全部完成才写报告；上下文变化时从台账和进度继续，不重新从头扫描。报告中间结论时明确阶段状态，不将阶段报告标为最终完成。

### 7. 完成标准

- 全部范围内文件、函数、模块级逻辑和非函数源码区间都有明确处理状态；人工逐行范围内的全部行已阅读，未完成部分不得标为完成。
- 全部当前范围需求都有实现映射或明确缺口；延期项与当前问题区分清楚。
- 跨模块关键链路、权限边界和数据状态转换均已核对，不以各模块各自通过代替端到端检查。
- 已确认问题均有可核查证据和逐项修复方案；候选问题、运行待验证、历史问题复核结果分别列出。
- UI 完成情况有页面/角色/状态清单及实际截图证据；环境不具备时明确保留动态 UI 审查未完成状态。
- 检查结果与当前审查基线匹配，测试跳过和环境阻塞没有被写成通过。
- 若逐行静态审查已完成但动态验收尚有阻塞，应明确写出两者各自的完成情况，不宣称整个项目已经验收通过。

最终回复提供所有交付物路径、实际覆盖范围、优先修复的问题及原因、修复实施次序、尚未完成的验证和下一步所需条件。不要声称“保证没有 bug”。
