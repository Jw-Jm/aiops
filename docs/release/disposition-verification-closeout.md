# 共用处置验证与执行关联

日期：2026-10-18。范围：非虚拟化功能开发，共用后检查报告与人工执行关联；没有新增 Pod/网络/硬件等具体配方，没有部署或远程验收。

## 已完成

- `relatedExecutionId` + `executionRelation` 明确关联一次新的继续处置或人工回退。绑定同一租户、Incident、集群/namespace、目标及 UID；只接受已完成成功/失败的原执行。关联参数进入风险确认摘要，在评估、确认、准备和派发阶段复查，不能沿用另一关系的确认，也不会自动填入命令或执行。
- 普通执行继续使用原 v1 Binding；有关联时使用 v2。数据仍保存在已有 Binding JSON 和审计中，没有新增执行器、审批人或数据库角色，也不需要迁移。新旧混合运行未验证，仍按统一交付基线要求冻结同一套源码/制品。
- 后检查生成 `command-post-check/v1` 冻结报告，与原标量结论、审计、持久事件同事务提交，审计保存报告摘要。记录执行/Incident/目标 UID、完成与观测/检查时间、配方、Evidence 引用、覆盖范围和明确结论原因。共用门禁拒绝缺授权、缺来源、事实不完整、旧观测等情况；可信完成还要求已验证归档与签名 Recipe。历史“不支持”按记录时适配范围保留，未来新增适配器不重解释旧报告。
- 读取接口复用现有 `/command-executions/{id}/post-check`，保留旧字段，提供结构化详情和有界的直接父子关系。读取及 SSE 都复查 Evidence/来源、Recipe 的当前权限，避免借冻结报告读取已撤回的引用。
- 前端展示冻结验证依据和证据入口，可查看原执行与后续执行、发起关联处置或人工回退。选择关联时清空实际命令并要求重新评估/确认；旧记录缺详情时明确提示，不生成虚构证据。关联列表最多一个直接原执行与最近 20 个后续执行，截断显式披露。
